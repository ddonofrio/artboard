# Drawing workflows

The pure catalog in `src/contracts/workflows.ts` defines workflows 1-7. Workflow 1 runs one artist without a reviewer and returns `unreviewed`, never approval. Workflow 2 runs an artist followed by an editable quality pass, with no separate reviewer. That pass judges visible evidence against the request, preserves a coherent viewpoint and silhouette, and favors a focused structural fix or a few local details over redrawing the scene. Workflows 3-7 run two through six creation stages followed by independent review. Workflow numbers match total stages, including a reviewer when enabled. Stage events count creation stages and the final review in their total. Other counts are rejected before execution. `runWorkflow` owns stage ordering and handoffs, and delegates tool/model execution to the agent loop. It imports no UI, filesystem or HTTP code. The package exposes the runner and catalog through `artboard/workflows`; role prompts live separately in `prompts.ts`.

Each stage gets the original prompt, a responsibility plan, the current scene JSON, the immediately preceding handoff and the accumulated history. Creation agents receive images only on demand through `scene_render`, once per call. With vision enabled, the reviewer automatically receives the exact submitted image at the start of each review; historical images are removed and later looks remain on demand. `finish_draft` requires `revision`, `done` and `not_done`; pending items carry an item and a reason. Nonfinal stages return `completed` without review. Only the final artist enters the independent review loop, with permission to correct earlier layers. Cancellation and incomplete results stop subsequent stages. The configured review limit preserves unresolved feedback. Foreground and specialist stages may do no work when the request does not need them.

Agent profiles override model IDs and extend built-in role instructions. Empty profile models use the configured default or one discovered chat model. Credentials and filesystem configuration remain with callers. Each `createTools` call must supply a fresh host; stage snapshots preserve revisions but have independent undo histories.

Role prompts contain the assigned work, responsibility for final corrections when applicable, the shared drawing cycle, and handoff fields. Each user message explicitly labels the drawing request and supplies the current scene and handoff data. Parameter descriptions remain with tools instead of being duplicated across role prompts. Private role instructions are appended once to the corresponding prompt.

Every creation role uses the shared drawing cycle: plan its assigned block, execute all planned edits, inspect the resulting image once, apply grouped corrections when needed, and inspect again before handoff. This applies to the final artist's reviewer corrections as well. A single call may contain a complete drawing block; multiple consecutive edit calls also work without intermediate inspection. JSON-only agents assess completed geometry and layers instead.
