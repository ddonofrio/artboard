# Drawing agents

The agent adapter tolerates `points` in place of `bounds` for ellipses, procedural objects and sprites, on creation and updates. A flat `[x,y,width,height]` is used directly; two or more `[x,y]` points define the bounding box. Explicit `bounds` take precedence. Normalization happens before core validation, preserves the original call arguments in the journal, and stores canonical geometry. Invalid geometry still rejects the entire batch.

This layer owns the drawing editor/reviewer workflow using AI SDK and the OpenAI-compatible provider. It imports the drawing core and exposes configuration, scoped tools, progress events, and orchestration through `artboard/agents`. It has no UI, filesystem, or Vite dependency.

Each run requires an isolated draft host. The editor starts with an empty canvas or the supplied base scene and draws through validated tool calls. Agents impose no separate operation cap: `scene_apply` uses the core contract, including its 128-operation batch bound. Agents do not use prebuilt recipes or file export tools. The standalone `runAgentLoop` submits a revision through `finish_draft`. Workflow stages additionally require `done` and `not_done` with reasons. The reviewer has read-only tools and returns `submit_review` with approval or actionable corrections for that exact revision. It cannot approve unresolved requirements reported by the final artist.

The standalone editor and workflow artists share the short instructions in `drawing-cycle.ts`: plan the assigned work, execute its drawing calls consecutively, check the completed block, group corrections, and submit the current revision. `prompts.ts` contains the editor/reviewer instructions and the explicit user-request wrapper. Workflow prompts add scope and handoff fields. System prompts remain stable between requests; scene revisions, palettes and correction data live in the current user context rather than being repeated as instructions. Tool schemas describe drawing parameters; unavailable features and unrelated output types are absent from the prompts. Successful edits do not require intervening inspection. UI previews remain independent of model inspection.

The editor receives current scene JSON after each tool, with images only on demand. With vision enabled, each reviewer pass automatically starts with the exact submitted draft image, including corrected drafts. Editor and reviewer may also call the read-only `scene_render` tool for another look. Each automatic or requested image (including crop/scale) is supplied for one inference only, then removed from retained history so old review images do not accumulate. Failed renders attach no image, and JSON-only mode omits both image inputs and the vision tool. UI previews and output persistence still render independently. Mutation feedback reports changed pixels and advisory coverage diagnostics. The reviewer retains its conversation across correction passes. Rejected drafts require a new revision and a visible mutation before resubmission. Approval stops immediately; review-limit exhaustion delivers the latest drawing with unresolved feedback. A failed or unfinished model response after canvas creation delivers an incomplete drawing and its error. Cancellation prevents final delivery.

The configuration bounds review rounds, output tokens, and individual request timeouts. Optional reasoning_effort sends none, low, medium or high to the compatible server; omission keeps its default. review=false delivers unreviewed without reviewer inference. Browser/CLI preview adapters use vision_image_divisor (default 4) to reduce model images only; external library hosts own their preview encoding. Tool steps do not have a fixed count limit. Model output remains validated data. The [loop detector](plugins/README.md) recovers request context after repeated identical tool failures without changing scene validation or consuming a review round.

The endpoint defaults to localhost; empty editor IDs discover a non-embedding model and empty reviewer IDs use the editor model. Only OpenAI-compatible `/models` and `/chat/completions` are used. Vision requires an adapter returning inline JPEG or PNG data URLs. There is no cloud fallback or silent downgrade to text-only review.

Progress callbacks expose request context without image bytes, response metadata, model-provided thinking, agent state, tools, previews, drafts, reviews, errors, and final results. State events report processing_prompt while assembling context, thinking while receiving model reasoning, writing_tool_args while receiving function arguments, executing_tool before dispatch, and idle at delivery. Transport requests SSE streaming. processing_prompt remains active through server prefill; thinking starts only when actual reasoning arrives, and writing_tool_args starts with streamed function arguments. Partial arguments are progress data; validated tools execute through the SDK when their call is complete. Usage is requested with the stream, and reasoning counts use reported reasoning_tokens or a clearly marked estimate of the full received reasoning. Stream errors retain partial scenes and do not trigger hidden retries. Thinking is read from reasoning_content, reasoning or inline think tags; diagnostic prompt snapshots still omit reasoning. The callback for a preview is awaited before the next tool executes. Callers own presentation and persistence. The [Node command](../../DEVELOPMENT.md) and local HTTP service supply filesystem/image adapters. The [workflow layer](../workflows/README.md), exposed at `artboard/workflows`, orchestrates creation stages and keeps review corrections with the final artist. The agent entry remains independent of that layer.

`listModels` normalizes the configured API URL and discovers model IDs with optional authentication and a ten-second timeout. Automatic agent discovery excludes embedding IDs; callers may pass `all` as its fourth argument to list all advertised valid IDs for an explicit selector.
